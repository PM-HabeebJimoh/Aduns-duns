# OKR Guide

Objectives and Key Results. One quarter. Written before the work starts.

## Shape

- **Objective** — qualitative, inspirational, time-bound. What we want to achieve and why it matters.
- **Key Results (2–5)** — measurable outcomes that prove the Objective was achieved.
- **Initiatives** (not KRs) — the projects/features you'll ship to move the KRs.

**Critical distinction:** KRs are *outcomes*, not *outputs*.

| ❌ Output (feature ship) | ✅ Outcome (user/business change) |
|---|---|
| Launch v2 of onboarding | Increase week-1 activation from 34% → 50% |
| Ship 3 integrations | Reach 30% of new signups using ≥ 1 integration |
| Redesign checkout | Reduce checkout abandonment from 22% → 15% |
| Write API docs | Reduce API-related support tickets by 40% |

If a KR can be marked "done" by shipping something regardless of whether users behave differently, it's an output, not a KR.

---

## Writing a good Objective

- **Inspirational** — the team should want to work on it
- **Qualitative** — no numbers in the Objective (numbers live in the KRs)
- **Time-bound** — one quarter
- **Aligned** — traces up to a company-level Objective

Examples:
- *"Make new teams successful in their first week."*
- *"Become the fastest way to publish a report."*
- *"Turn casual users into daily habits."*

---

## Writing a good Key Result

Each KR should be:

1. **Measurable** — a number, not an adjective
2. **Outcome-focused** — changes user or business behavior
3. **Time-bound** — by end of quarter
4. **Ambitious** — 70% attainment = success (if you routinely hit 100%, you're sandbagging)
5. **Owned** — one name

Format: **[Metric] from [baseline] to [target] by [date]**.

Example set:

> **Objective:** Make new teams successful in their first week.
> - **KR1:** Week-1 activation rate from 34% → 50% by Sep 30.
> - **KR2:** % of activated teams inviting a second user from 22% → 40% by Sep 30.
> - **KR3:** Median time to first "aha" event from 3h 40m → under 60 min by Sep 30.
> - **Guardrail:** Support ticket rate per 100 new teams must not increase.

## Grading

Score each KR 0.0–1.0 at end of quarter.

| Score | Meaning |
|---|---|
| 0.0–0.3 | Missed | Something was wrong (target, plan, execution) — debug |
| 0.4–0.6 | Progress | Real progress, didn't fully land |
| 0.7–1.0 | Delivered | On target |
| 1.0+ | Overshoot | Was the target too low? |

Average of KRs = Objective score. **Consistent 1.0s = ambition too low.** Aim for team average of 0.7.

---

## Cadence

- **Week 0:** Draft OKRs bottom-up + top-down, negotiate
- **Week 1:** Publish, share widely
- **Weekly:** 5-min check-in per KR (on track / at risk / off track)
- **Mid-quarter:** Formal review, adjust initiatives (not targets)
- **End of quarter:** Grade, retro, draft next quarter

---

## Anti-patterns

- **Output KRs disguised as outcomes** — "Launch feature X and hit 100 users" is still output-flavored. Rewrite to the user behavior.
- **Too many KRs** — >5 = no priorities. Cut.
- **Sandbagging** — hitting 1.0 every quarter means the target was safe. Push next time.
- **Moving the target mid-quarter** — kills trust. Adjust initiatives, not KRs.
- **OKRs = task list** — if it can be checked off by an individual, it's an initiative, not a KR.
- **Copy-paste from last quarter** — the world changed; the KRs should too.
